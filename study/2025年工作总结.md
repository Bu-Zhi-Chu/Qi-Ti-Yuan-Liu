2025 年度工作总结-李健

---

一、 年度工作回顾
2025 年对我来说是充实且“补课”的一年。在部门领导和同事的帮助下，我主要承担了 WebGIS 方向的开发任务。工作的重心从以往单纯的页面堆砌，逐渐转向了对三维可视化效果的打磨和底层性能的优化。
今年我的工作主要分为三块：一是基于 Cesium 和 Maptalks 的地图业务开发，这也是占用时间最多的部分；二是配合项目需求，用 Unity 制作了一些高保真场景；三是利用业余时间，对自己薄弱的前端基础进行了系统复习，并尝试写了一个低代码工具，希望能改善日常开发中重复劳动的现状。

---

二、 重点项目与技术攻坚

1. 三维地图与灌溉推演（CesiumJS）
   这是今年投入精力最大的项目。主要任务是在三维地球上展示灌溉区的全貌，并模拟水流灌溉的过程。刚开始做的时候并没有觉得很难，但随着地形数据和模型精度的增加，一系列性能和效果问题接踵而至。
   • 大场景加载的性能平衡
   项目初期，为了追求效果，我们加载了高精度的倾斜摄影模型和地形数据，结果导致浏览器的帧率一度掉到了 20 帧以下，操作非常卡顿。
   为了解决这个问题，我查阅了大量资料，反复调整 3D Tiles 的 maximumScreenSpaceError（屏幕空间误差）参数。这不是简单的调大或调小，而是在画质和流畅度之间找一个平衡点。同时，我配合后端同事对原始模型进行了轻量化处理，并加入了视锥体剔除逻辑，确保看不见的地方不渲染。经过两周的反复调试，最终将平均帧率稳定在了 50 帧左右，基本保证了交互的流畅性。
   • 灌溉推演的动态模拟
   业务方要求在地图上能看到“水流动的过程”，而不只是变色的线条。这是开发中的难点。
   起初我尝试用 GIF 贴图，但效果很假，而且没法控制流速。后来我决定啃一下“硬骨头”，从 Shader（着色器）入手。我编写了自定义的 GLSL 代码，通过控制纹理坐标随时间偏移，实现了水流沿着渠道流动的视觉效果。
   针对喷灌和滴灌场景，我使用了 Cesium 的粒子系统。这个过程比较繁琐，需要不断调整粒子的发射速度、生命周期和重力参数，才能让水雾看起来像真的一样。虽然最终效果离 3A 游戏还有差距，但也算是在 Web 端实现了比较直观的推演展示，得到了业务方的认可。
2. 二维地图的轻量化实现（Maptalks）
   在做一些数据管理类的模块时，我发现 Cesium 显得太“重”了，加载慢且消耗资源。在与团队沟通后，我负责引入了 Maptalks 作为二维地图方案。
   • 百万级点位的渲染
   项目中涉及灌溉设备的点位非常多。用普通的 Leaflet 加载几千个点就开始卡。我利用 Maptalks 基于 WebGL 的特性，重写了图层渲染逻辑。
   对于特别密集的区域，我写了一个简单的聚合算法，把相邻的点合并显示；对于路网和地块数据，我尝试了矢量瓦片（MVT）技术，把 GeoJSON 转成瓦片加载。这让地图在缩放和平移时非常顺滑，几乎没有延迟。
   • 二三维联动
   为了让用户体验更好，我做了一个联动功能：在 Maptalks 二维地图上点击某个灌溉片区，右侧的 Cesium 球体就会自动飞行到对应的三维视角。这个功能逻辑不复杂，但需要处理好两个地图引擎坐标系的转换（WGS84 与 GCJ02/BD09），避免位置跑偏。
3. 三维场景制作（Unity 3D）
   Web 端受限于浏览器性能，有些极高画质的汇报场景很难实现。所以，我也承担了部分 Unity 场景的制作任务。
   这部分工作我主要是作为一个执行者，负责搭建场景、烘焙光照贴图（Lightmap）以及调整材质细节。虽然 Unity 不是我的主攻方向，但通过这几个场景的制作，我对 PBR 材质流程和光影原理有了更直观的理解，反过来也帮助我在写 Web 前端 Shader 时有了更好的美术感觉。目前我也在尝试研究如何把 Unity 场景更好地导出给 Web 使用，不过这块技术比较复杂，目前还在探索阶段。

三、 个人成长：前端体系的查漏补缺
工作这几年，我一直有一种焦虑感：虽然能完成任务，但很多时候是“知其然不知其所以然”，也就是大家常说的“调包侠”。为了改变这种状态，今年我强迫自己慢下来，系统地重修了前端基础。

1. 深入 JavaScript 与框架原理
   不再满足于会用 API，我花时间去理解了 JavaScript 的事件循环机制、闭包内存管理以及原型链。在学习 Vue 和 React 的过程中，我尝试去阅读部分源码，理解虚拟 DOM 是如何通过 Diff 算法更新页面的。
   这些理论看似枯燥，但在解决复杂 Bug 时非常有用。比如以前遇到内存泄漏只知道重启，现在能通过 Chrome DevTools 去分析是不是有定时器没清除或者闭包引用了 DOM 节点。
2. 拥抱 TypeScript
   今年在自己的新代码中，我开始强制使用 TypeScript。刚开始觉得写类型定义很麻烦，降低了开发速度，但坚持了一段时间后，发现维护成本明显降低了。接口字段改动时，TS 报错能直接告诉我哪里需要修改，避免了很多上线后才发现的低级错误。

四、 业余尝试：自研低代码框架（进行中）
这是一个纯粹出于“偷懒”目的而发起的个人项目。
背景：
在日常开发中，我发现我们组大约有 30%-40%的工作量是在写各种后台管理的增删改查（CRUD）页面。这些页面逻辑很简单，但写起来很繁琐，大量的复制粘贴不仅枯燥，还容易出错。
进度（50%）：
利用周末和晚上的空闲时间，我尝试搭建了一套基于 Vue3 的前端低代码工具。目前大概完成了**50%**的进度：
• 已完成： 基础的拖拽编辑器做出来了，可以把输入框、按钮、表格拖到画布上，并生成对应的 JSON 配置。
• 进行中： 目前卡在“逻辑编排”这块。我希望能让用户通过连线的方式定义“点击查询 -> 发送请求 -> 刷新列表”这样的逻辑，但这块涉及到的状态管理比较复杂，还在攻坚中。
初衷与定位：
我做这个并不是为了造一个惊天动地的轮子，只是希望能搞出一个顺手的小工具。如果在明年的项目中，这个工具能帮大家少写几百行重复代码，我就觉得很满足了。

五、 不足与反思
回顾 2025 年，虽然干了不少活，但也有很多遗憾和不足：

1. 技术广度有余，深度不足： 看起来 Cesium、Maptalks、Unity 都能搞，但遇到真正的底层难题（比如 WebGIS 中的大规模并行计算、Unity 的高级渲染管线定制）时，还是感觉力不从心，缺少“专家级”的解决能力。
2. 低代码项目进度较慢： 毕竟是业余时间开发，加上中间因为业务忙停滞了一段时间，导致原计划年底出 Demo 的目标推迟了。目前框架还很粗糙，距离真正能用还有很长的路要走。
3. 沟通协作上的欠缺： 有时候埋头写代码，对业务需求的理解不够透彻，导致后期返工。以后在开发前，需要花更多时间跟产品和业务同事对齐需求。

---

六、 2026 年工作规划
新的一年，我希望能把手头的事情做得更扎实一些：

1. 深化 WebGIS 能力： 不再满足于调用 API，计划系统学习图形学（WebGL/WebGPU），希望能自己写出更酷炫、性能更好的地图特效，把 Cesium 的能力发挥到极致。
2. 落地低代码工具： 这是明年的硬指标。上半年（Q1-Q2）争取把剩下的 50%逻辑编排功能做完，下半年在组内找一两个非核心的小项目试用一下，哪怕只是用来生成简单的表单代码也好。
3. 探索端云结合： 继续研究 Unity 和 Web 的融合方案。如果能把 Unity 的高画质和 Web 的便捷性结合起来，对我们的项目演示会有很大帮助。
4. 多做分享： 把自己学到的 TS 技巧、性能优化经验整理出来，多在部门内部分享，大家一起进步。

---

结语：
感谢领导这一年的包容和指导，也感谢开发部兄弟们的支持。2026 年，我会继续保持学习的心态，踏踏实实写好每一行代码，争取在技术上能更进一步，为部门的项目交付贡献更多力量。
